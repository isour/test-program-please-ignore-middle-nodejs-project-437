Контракт API

Фронтенд магазина уже написан и собран. Он ожидает конкретные адреса, конкретные имена полей и конкретные коды ответов. Договорённость об этом называется контрактом: пока ваш сервер ему соответствует, фронтенд работает; отступите в любой мелочи — и экран останется пустым.

На этом шаге вы описываете контракт формально — в TypeSpec, и генерируете из описания спецификацию OpenAPI. Так делают в командах, где фронтенд и бекенд пишут параллельно: сначала договариваются о контракте, потом каждый реализует свою половину. Ваше описание — не документация задним числом, а то, что вы дальше реализуете и по чему проверяете себя.

Всё, что нужно описать, есть ниже. Реализовывать эндпоинты вы будете постепенно, на своих шагах; описать контракт целиком удобнее сразу.

Общие правила

  • Все эндпоинты живут под префиксом /api.

  • Тела запросов и ответов — JSON, кодировка UTF-8.

  • Имена полей — camelCase, ровно как ниже. Лишние поля в ответах допустимы, отсутствующие — нет.

  • Идентификаторы (id, productId, categoryId) — строки. Внутри базы это могут быть числа; наружу они уходят строками.

  • createdAt — момент времени в UTC в формате ISO 8601 (2026-07-01T08:00:00Z).

  • Числа приходят числами, а не строками. Ловушка тут в типе numeric: драйвер отдаёт его строкой, и {"amount": "32990"} уезжает клиенту как внешне рабочий ответ, нарушающий контракт.

  • Ошибки возвращаются в формате Problem Details (RFC 9457) — единый конверт на все случаи:

    1
    2
    3
    4
    5
    {
      "type": "/problems/email-taken",
      "title": "Email already taken",
      "status": 409
    }

    Поле type — из закрытого словаря (таблица ниже). Именно по нему фронтенд выбирает текст для пользователя, поэтому title и необязательный detail остаются техническими: их видит разработчик в логах, а не покупатель на экране.

    Формат ошибки задаёте вы, у фреймворка свой ответ по умолчанию, поэтому обработчик ошибок заводится один раз на всё приложение. Ошибки самого фреймворка проходят через него же. Тело запроса, которое не удалось разобрать, даёт 400 с типом validation-error, и 500 остаётся только для непредвиденных ошибок сервера.

ТипСтатусКогда

validation-error400тело или параметры не прошли проверку

Значение type записывается URI вида <адрес>/problems/<тип>. Адрес выбираете сами, подойдёт адрес вашего сервиса или относительный URI /problems/email-taken, который разрешает RFC 9457. Фронтенд узнаёт ошибку по последнему сегменту, поэтому тип пишется точно как в таблице.

В словаре есть ещё одно значение — about:blank, значение по умолчанию из RFC 9457. Его отдаёт не сервер: так фронтенд помечает ответ, который вообще не был Problem Details (например ошибку прокси). Отдавать about:blank из своего API не нужно.

Как устроена авторизация

Состояние входа хранится в сессии на сервере, ссылку на неё браузер держит в cookie. Фронтенд отправляет запросы с credentials: 'same-origin' — то есть cookie уезжает автоматически, потому что фронтенд и API живут на одном origin. Никаких заголовков Authorization и токенов в localStorage фронтенд не использует.

Что из этого следует для вас:

  • вход (POST /api/session) и регистрация (POST /api/users) открывают сессию — регистрация тоже, пользователь после неё сразу авторизован;
  • выход (DELETE /api/session) сессию завершает на сервере, а не только чистит cookie;
  • GET /api/me — единственный способ, которым фронтенд узнаёт, кто вошёл. Для анонима это 401, а не 200 с пустым телом;
  • cookie должна быть HttpOnly и Secure; конкретный механизм сессий — ваш выбор (плагин сессий с хранилищем, своя таблица). В cookie лежит только идентификатор сессии, а сама сессия хранится на сервере. Подписанная cookie с данными пользователя не подходит, потому что отозвать её нельзя, и после выхода сохранённая копия снова пускает.

Эндпоинты

GET /api/health

Проверка живости. Возвращает 200 и {"status": "ok"}. По этому эндпоинту проверка и хостинг ждут готовности приложения, поэтому он не должен зависеть от базы данных.

POST /api/users

Регистрация. Тело — Credentials. Успех — 201 и User, сессия открыта.

Занятый email — 409, тип email-taken. Email сравнивается без учёта регистра и внешних пробелов: Ivan@Example.COM с пробелом на конце и ivan@example.com — один и тот же адрес. Невалидное тело (не email, короткий пароль) — 400, тип validation-error.

1
2
3
curl -i -X POST http://localhost:8080/api/users \
      -H "Content-Type: application/json" \
      -d '{"email": "ivan@example.com", "password": "secret1"}'

POST /api/session

Вход. Тело — Credentials. Успех — 200 и User, сессия открыта.

Неизвестный email и неверный пароль дают одинаковый ответ 401 с типом invalid-credentials: иначе перебором узнаются существующие адреса.

DELETE /api/session

Выход. Успех — 204 с пустым телом. Сессия завершается на сервере: следующий GET /api/me обязан ответить 401, даже если браузер сохранил cookie.

GET /api/me

Текущий пользователь. Есть сессия — 200 и User. Нет — 401, тип unauthorized.

GET /api/categories

Справочник категорий: 200 и массив Category. Пустой справочник — 200 и [].

GET /api/promos

Промо-блоки главной: 200 и массив Promo. Товар приходит внутри блока, отдельного запроса за ним фронтенд не делает.

Пустой список — 200 и []: главная должна оставаться рабочей.

GET /api/products

Каталог с фильтрами и пагинацией. Все параметры необязательны.

ПараметрТипПо умолчаниюСмысл
categoryстрока—слаг категории; пусто или нет параметра — все категории
qстрока—подстрока названия, регистр не учитывается
priceMinцелое—нижняя граница цены, включительно
priceMaxцелое—верхняя граница цены, включительно
availableбулево—true — только доступные; нет параметра — все
pageцелое1номер страницы, минимум 1
perPageцелое6размер страницы, максимум 48

Отвечает 200 и ProductPage. Фильтры комбинируются: категория, цена, наличие и поиск применяются одновременно.

Фильтрация и пагинация выполняются на сервере. Отдать все товары и дать фронтенду отобрать нужные нельзя: фронтенд просто покажет всё, что пришло, а meta окажется неверным. Проверка это видит — она сверяет состав соседних страниц и реакцию выдачи на каждый фильтр.

Пустая выдача — не ошибка: 200, items: [], total: 0. Параметр не того типа — 400, тип validation-error.

Фронтенд присылает только заполненные фильтры и не присылает perPage — он полагается на значение по умолчанию.

1
curl "http://localhost:8080/api/products?category=videokarty&priceMax=50000&available=true&page=1"

GET /api/products/{id}

Товар есть — 200 и Product. Нет — 404, тип not-found.

Идентификатор — тот же, что в ответе каталога: фронтенд берёт его из списка и ставит в адрес страницы товара. Этот же эндпоинт вызывается для каждой позиции корзины после перезагрузки страницы — в браузере лежат только идентификаторы и количества.

POST /api/orders

Оформление заказа. Только для авторизованного: без сессии — 401, тип unauthorized.

Тело: { items, shipping }, где items — непустой массив CartItem, shipping — ShippingDetails.

Цен и итоговой суммы в запросе нет. Сервер сам находит товары по идентификаторам, берёт их текущие цены, считает total и записывает снимок в позиции заказа. Это не перестраховка: всё, что приходит из браузера, может быть подменено, и цена товара — первое, что подменят.

Успех — 201 и Order со статусом paid.

Ошибки:

  • method: delivery без непустого address — 400, тип address-required;
  • хотя бы один товар не найден или available: false — заказ не создаётся целиком, ответ 400, тип unavailable-items, и в теле поле unavailableProductIds со списком всех проблемных идентификаторов, а не первого попавшегося;
  • пустой items, отсутствующее обязательное поле, quantity меньше 1 — 400, тип validation-error.

curl -i -X POST http://localhost:8080/api/orders \
      -H "Content-Type: application/json" \
      -b cookies.txt \
      -d '{"items": [{"productId": "1", "quantity": 2}],
           "shipping": {"method": "pickup", "recipientName": "Иван", "phone": "+70000000000"}}'

GET /api/orders

Заказы текущего пользователя, новые первыми. Без сессии — 401. Заказов нет — 200 и [].

Отдавать чужие заказы нельзя — это самая дорогая ошибка в проекте: проверка регистрирует второго пользователя и убеждается, что его кабинет пуст.

GET /api/orders/{id}

Свой заказ — 200 и Order. Чужой или несуществующий — 404, тип not-found. Именно 404, а не 403: подтверждать существование чужого заказа не нужно.

Чего в этом контракте нет

Контракт учебный, и часть решений в нём упрощена сознательно. Знать про упрощения полезно: в рабочем проекте их не прощают.

  • 400 там, где по смыслу 422. Недоступный товар в заказе — это синтаксически валидный запрос с невыполнимым содержимым; такие ответы часто отдают как 422 Unprocessable Content. Мы оставили 400, чтобы не заводить лишний код.
  • Ошибки без разбивки по полям. У нас один type на весь запрос. Клиенту, который подсвечивает конкретный инпут, нужен список: {"errors": [{"field": "shipping.phone", ...}]}. Формат Problem Details это допускает — расширяется своими полями, как у нас сделано с unavailableProductIds.
  • Тип содержимого ошибок — application/json, а не application/problem+json. По RFC верен второй; мы оставили первый, чтобы не заводить особый случай в клиенте.
  • Нет защиты от двойного оформления. Два одинаковых POST /api/orders создадут два заказа. В платёжных API от этого защищаются ключом идемпотентности: клиент присылает Idempotency-Key, сервер по нему возвращает уже созданный заказ вместо нового.
  • Нет остатков. У товара булев available, а не количество. Настоящий магазин списывает остаток в транзакции и блокирует строку, чтобы двое не купили последнюю видеокарту.
  • Сортировка каталога не параметризована. В продовом API к списку почти всегда добавляют sort.

Как поставить TypeSpec

TypeSpec — инструмент из мира Node.js, и в проекте он нужен только для описания контракта. Поставьте его в package.json в корне проекта. Если файла ещё нет, создайте его командой npm init -y, и на шаге про фронтенд пакет с фронтендом встанет в этот же файл.

1
npm install -D @typespec/compiler @typespec/http @typespec/openapi @typespec/openapi3

Настройка генератора — файл contract/tspconfig.yaml. Он говорит, куда положить готовую спецификацию:

        emitter-output-dir: "{project-root}"

Задачи

  1. Поставьте TypeSpec и создайте каталог contract/ с main.tsp и tspconfig.yaml.
  2. Опишите модели из раздела «Модели» и все двенадцать операций из раздела «Эндпоинты» — с параметрами, телами, кодами ответов и моделью ошибки.
  3. Опишите словарь типов ошибок как закрытое перечисление: новый случай должен начинаться с правки контракта, а не с новой строки где-то в коде.
  4. Настройте генерацию OpenAPI и сгенерируйте contract/openapi.yaml. Закоммитьте оба файла.
  5. Добавьте генерацию в Makefile отдельной целью, чтобы спецификацию можно было пересобрать одной командой.
  6. Сверьте описание с этим шагом: каждый путь, параметр, поле и код ответа должны совпасть.

Подсказки

  • Начните с моделей, потом опишите операции — так короче: Product переиспользуется в каталоге, в карточке и внутри промо-блока.

  • Модель ошибки удобно описать один раз и переиспользовать во всех операциях.

  • Спецификация — не украшение. Если по ней сгенерировать mock-сервер и подключить к нему фронтенд, экраны отрисуются на выдуманных данных. Это быстрый способ убедиться, что вы описали контракт, а не что-то похожее:

    1
    npx @stoplight/prism-cli mock -h 0.0.0.0 -p 4010 -m false contract/openapi.yaml

  • Если фронтенд не работает и вы не понимаете, чем ваш ответ отличается от ожидаемого, запустите проверку и загляните в артефакты упавшего прогона: в них лежит эталонная спецификация API — tmp/artifacts/contract/openapi.yaml. Сверяйте по ней пути, тела и коды ответов.

Результат шага

Контракт описан в TypeSpec, из него сгенерирована спецификация OpenAPI, и вы точно знаете, какие ответы предстоит реализовать.
