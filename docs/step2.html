Настройка проекта

На этом шаге вы поднимаете бекенд без фронтенда и добиваетесь, чтобы он отвечал на первый запрос к API. Важно, чтобы приложение запускалось одной командой и брало настройки из окружения.

Ключевое требование — фронтенд и API живут на одном порту. Фронтенд обращается к API по относительным путям /api/..., то есть по тому же адресу, с которого он загружен. Отдельного адреса у API нет, настраивать CORS не нужно. Это же условие делает работоспособной сессионную cookie: она ставится и отправляется в пределах одного origin.

Требования

  • Приложение запускается сервером на порту из переменной окружения PORT, по умолчанию — 8080.
  • Слушает 0.0.0.0, а не 127.0.0.1: иначе снаружи контейнера порт не виден.
  • Подключение к базе берётся из переменной окружения DATABASE_URL. Своё значение в коде не зашито.
  • Статика и API отвечают на одном порту: статика с /, API с /api/....
  • GET /api/health возвращает 200 и {"status": "ok"}. По этому адресу проверка ждёт готовности приложения, поэтому он не должен зависеть ни от базы, ни от собранного фронтенда.
  • В Makefile есть цели lint и test. Первая запускает линтер, вторая ваши тесты.

Фреймворк выбираете сами. Примеры в шагах показаны на Fastify, но контракт не требует ни его, ни конкретной версии Node.js: проверка видит только ответы по HTTP.

  const app = Fastify(options);

  app.get('/api/health', async () => ({ status: 'ok' }));

  return app;

Так его можно собрать с другими зависимостями в тестах, и пул соединений не открывается при импорте модуля. Точка входа остаётся тонкой и читает порт из окружения:

Линтер и тесты

Линтер и тестовый раннер выбираете сами и подключаете сейчас, чтобы тесты росли вместе с кодом. Пишите тесты по возможности на каждый сценарий и заранее подумайте, что в приложении можно проверить и как. Обе команды собираются в Makefile под именами lint и test, и CI на следующих шагах зовёт именно их.

Проверка ваш Makefile не вызывает — она запускает приложение целиком, в контейнере (об этом следующий шаг). Поэтому имена целей выбираете вы; здесь они такие же, как в примерах шагов.

Одно требование к запуску всё же есть, и оно про повторяемость: команда старта будет применять миграции и заливать каталог, а запускаться она будет много раз. Второй запуск не должен ни падать, ни задваивать данные. К этому вернётесь на шаге про базу.

Задачи

  1. Инициализируйте репозиторий и проект: npm init, подключите фреймворк и драйвер базы.

  2. Сделайте точку входа и фабрику приложения.

  3. Реализуйте первый маршрут GET /api/health, который возвращает {"status": "ok"}.

  4. Возьмите порт из PORT, а строку подключения к базе — из DATABASE_URL. К базе пока можно не подключаться, но значение должно читаться из окружения, а не из кода.

  5. Поставьте линтер и добейтесь, чтобы он проходил без замечаний.

  6. Поставьте тестовый раннер и, если получается, напишите первый тест.

  7. Соберите команды в Makefile, включая lint и test, и запустите приложение:

    1
    2
    3
    4
    $ make install && make start

$ curl http://localhost:8080/api/health
{"status":"ok"}

Результат шага

Приложение запускается одной командой, берёт порт и адрес базы из окружения и отвечает на первый запрос к API. Линтер проходит без замечаний, а make test запускает тесты.
