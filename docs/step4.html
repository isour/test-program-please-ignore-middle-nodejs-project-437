Фронтенд и запуск в контейнере

Фронтенд магазина написан за вас: это готовое одностраничное приложение, которое ходит в ваш API. На этом шаге вы подключаете его, видите магазин своими глазами и упаковываете приложение в образ.

Шаг идёт в два такта. Сначала вы раздаёте фронтенд статикой — интерфейс откроется, но данных в нём не будет: главная покажет ошибку загрузки, каталог останется пустым. Потом вы отдаёте три ручки каталога заглушками с захардкоженными данными, и магазин оживает целиком, ещё до появления базы.

Заглушки — временные. На шаге про базу вы замените их запросами, а состав данных перенесёте в миграции и заливку. Смысл этого такта не в них, а в том, чтобы дальше вы реализовывали API, уже видя, как он выглядит для пользователя.

Требования

Дальше всё держится на контракте запуска — это то, что проверка знает о вашем решении. Больше она не знает ничего: ни языка, ни фреймворка, ни ваших команд.

  • В корне репозитория лежит Dockerfile. По нему проверка собирает образ и запускает приложение.
  • Собранный образ запускается без дополнительных действий: миграции, заливка данных и старт сервера происходят при запуске контейнера.
  • Приложение слушает порт из переменной окружения PORT.
  • Подключение к базе берётся из DATABASE_URL. Саму базу проверка предоставляет.
  • Статика отдаётся с /, API — с /api/..., на одном порту.
  • Любой адрес, который не начинается с /api/ и не указывает на существующий файл, отдаёт index.html (SPA-fallback).
  • Неизвестный путь внутри /api/ отдаёт 404 в формате JSON, а не index.html.

Подключение фронтенда

Фронтенд приезжает npm-пакетом с уже собранным приложением. Собирать его не нужно — только положить файлы туда, откуда их раздаёт ваш сервер:

npm init -y
    npm install @hexlet/js-online-store-frontend

Файлы лежат в пакете в каталоге dist. Разложите их в public/:

Каталог images в пакете — заглушки изображений товаров. Пути к ним вы подставите в данные каталога на шаге про базу.

Раздача статики и адреса экранов

Фронтенд — одностраничное приложение. Часть его адресов входит в контракт, потому что проверка открывает их напрямую:

АдресЭкран
/главная с промо-блоками (не каталог)
/cartкорзина
/accountличный кабинет
адрес, заканчивающийся идентификатором товаракарточка товара

Все они должны открываться прямой ссылкой, в том числе после перезагрузки страницы. Значит, сервер обязан отдавать index.html на любой адрес, который не начинается с /api/ и не указывает на существующий файл. Без этого правила прямой заход на /cart даст 404.

Статику отдаёт плагин, и своих файлов он отдаёт сама — дописать нужно только SPA-fallback. У Fastify для этого есть обработчик «маршрут не найден»: запрос попадает в него уже после того, как ни дерево маршрутов, ни статика ничего не нашли. Там и стоит развилка — путь внутри /api/ отдаёт JSON-ошибку, остальное отдаёт index.html.

app.setNotFoundHandler((request, reply) => {
      if (request.url.startsWith('/api/')) {
        reply.code(404).send({ type: '...', title: 'Resource not found', status: 404 });
    
        return;
      }
    
      reply.sendFile('index.html');
    });

Перехватывающий маршрут вида /* для этого не годится: он подошёл бы и под /api/products, и фронтенд начал бы получать HTML вместо ответа API. В консоли браузера это выглядит как SyntaxError: Unexpected token '<'.

По той же причине неизвестный путь внутри /api/ обрабатывается отдельно, до перехватчика статики, и отвечает JSON-ошибкой в формате контракта.

Заглушки каталога

Чтобы увидеть магазин с данными, ответьте захардкоженными списками на три адреса. Формат — из вашего контракта:

  • GET /api/categories — массив категорий;
  • GET /api/products — объект {items, meta}, а не просто массив;
  • GET /api/promos — массив промо-блоков, у каждого товар вложен целиком.

Двух-трёх позиций в каждом списке достаточно: полный состав каталога с минимумами из чек-листа появится вместе с базой.

Ещё один адрес нужен ровно один ответ: GET /api/me анонимному посетителю отвечает 401. Пока авторизации нет, отдавайте 401 всегда. Ответ 200 с пустым телом фронтенд считает признаком незавершённой загрузки и остаётся в состоянии «загружаемся» навсегда.

Корзина заработает сама: она живёт в браузере, сервер о ней ничего не знает.

Dockerfile

Первая стадия дана готовой — она про наш npm-пакет, а не про ваш код:

1
2
3
4
5
# Собранный фронтенд Хекслета: из пакета берётся готовый бандл.
    FROM node:26-alpine AS frontend
    WORKDIR /build
    COPY package.json package-lock.json ./
    RUN npm ci --omit=dev

Дальше напишите сами. У вас единственный случай в проекте, когда отдельная стадия сборки не нужна вовсе: рантайм тот же node, и пакет с фронтендом ставится вместе с остальными зависимостями.

  1. установка зависимостей без dev-пакетов;
  2. копирование вашего кода;
  3. раскладка собранного фронтенда из пакета в каталог статики — той же командой, что локально;
  4. команда запуска, которая применяет миграции, заливает данные и поднимает сервер.

Первая стадия из примера выше тогда не понадобится: она нужна языкам, у которых рантайм другой.

Рядом положите .dockerignore, иначе в образ уедут и зависимости с хоста, и локально собранная статика с другими хешами в именах:

.git

    tmp
    public/assets

EXPOSE в файле не нужен: порт приходит из PORT, и фиксированное число здесь врало бы.

Миграции и заливка данных выполняются при запуске контейнера, а не при сборке образа. На сборке базы нет, и обращение к ней сломало бы её.

Задачи

  1. Подключите пакет с фронтендом и разложите его dist в каталог, откуда сервер раздаёт статику.

  2. Настройте раздачу статики и SPA-fallback. Проверьте, что файлы отдаются файлами:

    1
    2
    $ curl -sI http://localhost:8080/assets/$(ls public/assets | head -1) | grep -i content-type
    content-type: text/javascript

    Если здесь text/html — fallback перехватил статику, посмотрите порядок маршрутов.

  3. Проверьте прямой заход и JSON-404:

    1
    2
    3
    4
    5
    $ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/cart
    200
    
    $ curl -s http://localhost:8080/api/nothing-here
    {"type":"/problems/not-found","title":"Resource not found","status":404}

  4. Отдайте заглушками GET /api/categories, GET /api/products, GET /api/promos и 401 на GET /api/me. Откройте магазин: на главной появятся промо-блоки, из шапки откроется каталог, товар положится в корзину.

  5. Напишите Dockerfile и .dockerignore. Соберите и запустите образ так, как это сделает проверка:

    1
    2
    3
    export DATABASE_URL=postgres://postgres:password@localhost:5432/appdb
    docker build -t online-store .
    docker run --rm -e PORT=8080 -e DATABASE_URL="$DATABASE_URL" -p 8080:8080 online-store

    В контейнере нет вашего рабочего каталога — работает только то, что уехало в образ. Если файл попал в .dockerignore по ошибке, всплывёт это здесь.

Подсказки

  • В образ ставятся только зависимости, нужные приложению для работы. Тесты и линтер там лишние. Посмотрите и на команду запуска, потому что некоторые менеджеры пакетов перед стартом синхронизируют окружение и доставляют зависимости для разработки уже в работающем контейнере.

Результат шага

Магазин открывается в браузере с данными из заглушек, а приложение собирается в образ и запускается из него — тем же способом, которым его запустит проверка.
