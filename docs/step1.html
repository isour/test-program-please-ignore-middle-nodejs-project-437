Описание проекта В этом проекте вы разрабатываете бекенд интернет-магазина комплектующих для компьютеров: регистрацию и авторизацию, каталог с фильтрами и пагинацией, промо-блоки главной страницы, оформление заказа и личный кабинет с историей заказов. Данные храните в PostgreSQL. Фреймворк выбираете сами — примеры в шагах приведены на Fastify, но подойдёт любой. Фронтенд писать не нужно: готовое приложение предоставляет Хекслет. Вы подключаете его к своему серверу, и дальше оно работает ровно настолько, насколько ваше API соответствует контракту. Что получится — посмотрите скриншоты всех экранов магазина: главная, каталог, карточка товара, корзина, оформление, кабинет. Это то, что заработает поверх вашего бекенда. Предметная область Прежде чем проектировать схему данных и эндпоинты, разберитесь, чем оперирует магазин. Сущностей шесть. Категория — раздел каталога: идентификатор, слаг (videokarty) и название. Категории — справочник: они заданы заранее и не создаются пользователем. Товар — позиция каталога: название, описание, цена, категория, изображение и признак доступности. Товары тоже заданы заранее: их заливает ваш сервер при запуске, пользователь их только смотрит и покупает. Промо-блок — рекламный блок главной страницы: заголовок, текст и товар, на страницу которого блок ведёт. Хранится в базе, а не в вёрстке. Пользователь — покупатель: email и пароль. Появляется только регистрацией. Заказ — оформленная покупка: пользователь, состав, данные получения, итоговая сумма, статус и момент создания. Позиция заказа — товар внутри заказа: количество, а также снимок названия и цены на момент покупки. Позиция существует только внутри своего заказа. Связи: товар принадлежит одной категории, промо-блок ссылается на один товар, заказ принадлежит одному пользователю и содержит одну или несколько позиций. Корзина живёт в браузере, а не у вас. Это важное следствие для схемы: сущности корзины на бекенде нет. Фронтенд хранит в браузере только идентификаторы товаров и количества, а названия и цены каждый раз перечитывает из каталога. Ваш сервер узнаёт состав корзины единственный раз — в запросе на оформление заказа. Жизненный цикл заказа. Созданный заказ сразу получает статус paid. Других состояний нет, смены статуса и отмены нет — заказ неизменяем с момента создания. Почему в позициях снимок цены. Цена товара в каталоге со временем меняется, а в истории заказов должна остаться та, по которой купили. Поэтому название и цена копируются в позицию при оформлении, и заказ становится самодостаточным: он не «ломается», если товар подорожал или исчез из каталога. Чего в магазине нет. Не проектируйте под то, чего в задаче нет, иначе схема разрастётся зря: оплаты — заказ оформляется без денег, total только рассчитывается; остатков на складе — у товара есть булев признак доступности, а не количество; корзины на сервере — она целиком в браузере; смены статуса, отмены и возврата — заказ создаётся сразу оплаченным; администратора и управления каталогом — товары появляются заливкой данных; доставки как процесса — сохраняются только способ получения и контакт получателя. Всё это есть в настоящих магазинах, и часть можно добавить уже после сдачи — список идей собран в разделе «Что дальше» чек-листа. Как устроена работа Что делаем. HTTP API по описанному контракту плюс схему базы данных под него. Структуру кода, фреймворк и способ работы с базой выбираете сами. Что подключаем. Готовый фронтенд от Хекслета — npm-пакет с собранным приложением. Ваш сервер раздаёт его статику и отвечает на запросы /api/... на том же порту. Как проверяем. Проверка собирает образ по Dockerfile из вашего репозитория, запускает его и дальше говорит с приложением только по HTTP. Про язык, фреймворк и ваши команды она не знает ничего — это и есть контракт запуска. Против запущенного приложения работает набор браузерных тестов Хекслета: они поднимают фронтенд Хекслета поверх вашего сервера и проходят пользовательские сценарии целиком — зарегистрироваться, отфильтровать каталог, набрать корзину, оформить заказ, найти его в кабинете. Тесты не знают, как устроен ваш код: они видят только то, что видит пользователь. Поэтому падение теста означает, что ваше API ответило не так, как ожидает фронтенд. Что пишете сами. Спецификацию API в TypeSpec по описанию из шагов, Dockerfile, тесты на своё API и CI. На последних шагах разворачиваете проект на Render и подключаете сборщик ошибок. Чему научитесь Проект закрепляет то, что вы прошли: проектирование схемы базы данных, работу с ней из JavaScript, автоматическое тестирование и непрерывную интеграцию. Добавляются три вещи, которые отличают работу над настоящим сервисом: разработка по контракту, когда формат ответов задан заранее и менять его нельзя; чужой клиент, которого нельзя подправить под свою реализацию; и недоверие к клиенту — цены и итог считает сервер, потому что данным из браузера верить нельзя. Задачи Разберитесь, что предстоит собрать: HTTP API магазина с данными в PostgreSQL, поверх которого работает готовый фронтенд. Подготовьте окружение к разработке: Node.js 22, PostgreSQL и Docker. Docker нужен потому, что по образу вас проверяют.
