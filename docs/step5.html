Тесты и непрерывная интеграция

Тесты вы пишете сами и на каждый сценарий, который реализуете на следующих шагах. Они бьют по API напрямую: код ответа, тело, поведение на некорректных данных. По ним удобно вести разработку, потому что прогон занимает секунды и указывает на конкретный эндпоинт. Зелёный CI на каждом пуше делает эту проверку постоянной.

Ссылки

  • GitHub Actions
  • Сервисные контейнеры в GitHub Actions
  • Начинаем писать тесты (правильно)

Требования

  • Свои тесты запускаются целью make test из корня репозитория и не требуют браузера.
  • CI запускает make lint и make test на каждый пуш, прогон зелёный.
  • Тесты работают с отдельной базой и перед прогоном приводят её в известное состояние. Тогда второй прогон не падает на данных первого.

Заготовка workflow

Непрерывную интеграцию вы разберёте в отдельном курсе — здесь достаточно рабочей заготовки. Положите её в .github/workflows/main.yml и доведите под свой проект: имена своих команд и версию Node.js.

name: main
    on: [push, pull_request]
    
    jobs:
      tests:
        runs-on: ubuntu-latest
        services:
          db:
            image: postgres:18
            env:
              POSTGRES_PASSWORD: password
              POSTGRES_DB: appdb
            options: >-
              --health-cmd pg_isready --health-interval 5s --health-timeout 5s --health-retries 10
            ports: ['5432:5432']
        env:
          DATABASE_URL: postgres://postgres:password@localhost:5432/appdb
        steps:
          - uses: actions/checkout@v4
          - uses: actions/setup-node@v4
            with:
              node-version: 26
          - run: make install
          - run: make build
          - run: make lint
          - run: make test

Задачи

  1. Напишите первые тесты на API: GET /api/health отвечает 200, а неизвестный путь внутри /api/ отвечает 404 в JSON. Раннер и цель make test вы настроили на первом шаге, убедитесь, что они запускают эти тесты.
  2. Настройте GitHub Actions по заготовке выше: PostgreSQL сервисным контейнером, установка зависимостей, сборка, make lint и make test.
  3. Добейтесь, чтобы workflow был зелёным, и добавьте в README.md бейдж своего workflow. Бейдж hexlet-check показывает автопроверку Хекслета, ваши тесты он не отражает.
  4. Дальше на каждом шаге пишите тест на новый сценарий до или сразу после реализации.

Подсказки

  • Для своих тестов удобно поднимать приложение как обычно и бить по нему HTTP-клиентом: тест проверяет то же, что увидит фронтенд, включая сериализацию JSON. Тесты на уровне классов сериализацию как раз не проверяют, а ошибки контракта живут чаще всего именно в ней.
  • Сценарии с авторизацией удобно проверять клиентом, который умеет хранить cookie между запросами (curl -c/-b, CookieJar в вашем HTTP-клиенте). Без этого GET /api/me после входа будет отвечать 401, и вы будете искать ошибку в коде, а не в тесте.

Результат шага

Свои тесты на API запускаются одной командой, а CI зелёный на каждом пуше.
